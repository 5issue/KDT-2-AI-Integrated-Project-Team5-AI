# 에러 분석 + 2차 실험 보고서 (개선 가설·결과)

## 0. 요약

1차 구현을 실제 데이터로 돌려 **조용히 틀린 것 7건**을 찾았습니다. 전부 예외를 던지지 않고
그럴듯한 결과를 내던 것들이라 테스트가 아니라 **측정**으로만 잡혔습니다.

| | 증상 | 영향 | 상태 |
| --- | --- | --- | --- |
| E1 | 배치 재제출을 파일 이름으로만 판정 | 재료 매칭 **-15.6%p** | 미수정(설계 확정) |
| E2 | NULL 재고를 품절로 해석 | `reorder_candidates` 항상 0행 | 수정 |
| E3 | 버블 뷰가 레시피마다 재집계 | 홈 첫 쿼리 335ms | 수정 |
| E4 | EXPLAIN 버퍼를 재귀로 합산 | 성능 수치 **8.5배 과대** | 수정 |
| E5 | 한 글자 재료명을 버림 | 재료줄 **648줄 유실** | 수정 |
| E6 | 조인 결과 grain 이 어긋남 | 보관법 최대 **19배 중복** | 수정 |
| E7 | 문구 채점기 오탐 5종 | 실험 수치가 흔들림 | 수정 |

2차 실험(추천 문구)은 가설 2개로 **루브릭 평균 6.75 -> 8.24**(통과율 28% -> 84%)를 얻었지만,
**판정자 교차 검증에서 그 숫자가 판정자에 크게 좌우되는 것**을 확인했습니다(4절).
결론은 "점수를 게이트로 쓰지 말고 항목 순위를 나침반으로 쓴다" 입니다.

## 1. 에러 분석

### E1. 배치 재제출을 파일 이름으로만 판정 (가장 컸습니다)

`batch/client.py` 의 `pending_parts()` 가 입력 파일의 **이름**만 보고 재제출 여부를
정합니다. `BatchJob` 에 내용 지문이 없습니다.

```
09-10  r2_part001_input.jsonl 을 29 요청으로 제출 -> completed
09-15  새 데이터가 들어와 같은 이름으로 63 요청짜리를 다시 생성
09-15  submit 이 "살아 있는 배치가 있다" 며 건너뜀
09-15  collect 가 새 입력 63 에 옛 출력 29 를 짝지음 -> 34 요청 증발
```
**매니페스트에는 이상이 없습니다**(두 파트 모두 `completed`, `error_file_id: null`).
미매칭 2,685줄을 전수 분해한 결과입니다.

| 원인 | 줄 | 전체 12,879줄 대비 |
| --- | --- | --- |
| **물었는데 응답이 안 옴** | **2,003** | **15.6%p** |
| LLM 이 "마스터에 없다" 판정 | 662 | 5.1%p |
| 물어본 적 없음 | 20 | 0.2%p |

> 이 분석 전에는 "79%가 천장이고 남은 것은 마스터 공백" 이라고 보고했습니다.
> **상위 20종만 보고 단정한 것이 틀렸습니다.** 롱테일의 성격이 머리와 달랐습니다.

**조치(설계 확정, 미구현):** `BatchJob.input_sha256` + `pending_parts` 가 (이름, 해시)로 비교.
`collect` 에서 요청 수 != 응답 수면 경고.

### E2. NULL 재고를 품절로 해석

`reorder_candidates` / `missing_ingredient_products` 가 `COALESCE(stock_quantity, 0) > 0`
으로 걸렀습니다. **적재분 2,553행 전부 NULL** 이라 결과가 항상 비었습니다. 팀 정규화 가이드
4.3 은 NULL 을 **"수량 미상"** 으로 정의합니다 - 품절이 아닙니다. `IS NULL OR > 0` 으로
고쳤고 `seed-demo` 가 숫자를 채운 뒤 5행이 나옵니다.

> 빈 결과는 예외를 던지지 않습니다. **"결과가 0행" 을 정상으로 넘기면 이런 버그가 끝까지
> 숨습니다.** 시드 데이터가 있어야 잡힙니다.

### E3 / E4. 성능 수치와 성능 자체

버블 뷰가 (버블 x 레시피) 쌍마다 재료 집계를 다시 돌았습니다. 5 x 1,086 = **5,430회**.
집계가 버블에 의존하지 않는 것이 핵심이라, 레시피당 한 번 `{분류: 개수}` jsonb 를 만들어
두고 버블 규칙이 그 맵만 더하게 고쳤습니다(alembic `0010`): **232,931 블록 335ms -> 416 블록 30ms.**

고치는 과정에서 **측정 도구 자체가 틀린 것**도 나왔습니다. PostgreSQL 은 EXPLAIN 버퍼를
상위 노드에 **누적** 보고하는데 자체 스크립트가 자식을 재귀로 더하고 있었습니다.
"197만 블록" 이 실제로는 232,931 이었습니다(**8.5배 과대**). 더 나쁜 것은 그 상태로 정한
예산 100,000 이 **회귀 두 건을 놓쳤다**는 점입니다(46,698 / 49,645).
루트 노드 기준으로 고치고 예산을 20,000 으로 내렸습니다.

### E5 / E6. 파싱과 조인 grain

**한 글자 재료를 버렸습니다.** `len(name) < 2` 규칙 하나로 `물`(239) `꿀`(83) `무`(76)
`배`(64) 등 **648줄**이 사라졌습니다. 마스터 1,028종 중 41종이 한 음절이라, 한국어 재료에
한 글자는 예외가 아니라 흔한 경우입니다.

**many-to-one 조인을 LIMIT 앞에서 펼쳤습니다.** 같은 버그가 세 쿼리에서 나와 13종을
전수 점검했고, `product_storage_guideline` 이 같은 (위치, 맥락)을 최대 **19번** 돌려주는
것을 찾았습니다. 게다가 중복 160조 중 **125조는 기간이 서로 달랐습니다**(게류 냉장 구매후:
`10-12개월` vs `2-4 일`). 가장 짧은 기간을 고르도록 하고 `test_query_grain.py` 로 고정했습니다.

### E7. 채점기 오탐 5종 (2차 실험 중 발견)

추천 문구 실험을 돌리자 **채점기가 먼저 틀렸습니다.**

| 오탐 | 무엇이 걸렸나 |
| --- | --- |
| 레시피 이름 | `물파래콩전` 안의 `물`, `치즈토마토 가지구이` 안의 `치즈` 를 재료로 셈 |
| 판정 토큰 충돌 | 판정어 `예` 가 프롬프트 예시 라벨 `예:` 와 겹쳐 판정 줄이 통째로 누락 |
| 수량 단위 / 동사 | `재료 네 가지`, `가지고 계셔서` 의 `가지` 를 채소로 셈 |
| 한자어 | `달콤함을 배가시켜` 의 `배` 를 과일로 셈 |

전부 회귀 테스트로 고정했습니다. 한국어 동음이의어는 문자열 검사로 완전히 가릴 수 없으므로
예외 목록에는 **실제로 부딪힌 것만** 넣습니다. 미리 채우면 진짜 환각을 놓칩니다.

> **교훈:** 채점기를 못 믿으면 프롬프트를 고칠 수 없습니다. 이 구간에서 자동 검사 수치가
> 88% -> 100% -> 80% -> 100% 로 흔들렸고 그 사이의 비교는 전부 무의미했습니다. 수치가
> 움직이면 **대상이 바뀐 것인지 자로 잰 방식이 바뀐 것인지**부터 가르세요.

## 2. 2차 실험 — 설계

**대상**은 `/recommendations/my-recipes` 의 추천 문구 한 줄, **입력**은 상황 25건
(`rag_lab/experiments/openLeeWorld/cases.jsonl`)입니다. 실제 적재 레시피·재료 기반이고
부족 0/1/3개 이상·상비재료만 부족·조리시간 없음·빈 냉장고·프롬프트 인젝션을 경계 사례로
포함합니다.

**평가**는 `사람이 쓴 문서/rag 평가 지표 종류.md` 7절의 8항목, 각 0~10점, **통과선 평균 7.5**
입니다. 생성 `openai/gpt-4.1-mini`, 판정 `openai/gpt-4.1`(둘 다 OpenRouter). 판정자는
생성 모델과 다르게 강제합니다(`JUDGE_MODEL`) - 같으면 조립 시점에 거부합니다.

## 3. 2차 실험 — 가설과 결과

### 1차 관측 (`v4`): 평균 6.75, 통과율 28%

항목별로 보니 바닥 둘이 뚜렷했습니다 - `goal` **4.64**("행동 유도가 부족"),
`differentiation` **4.96**("상황에 상관없이 쓸 수 있는 상투적 문구"), `attractiveness` 5.52.
반대로 `clarity` 9.20 / `brevity` 9.64 는 처음부터 문제가 없었습니다.

`differentiation` 이 낮은 이유는 출력에 바로 보입니다. **25건 중 21건이 "신선한 ~" 으로 시작**
했습니다. 문자열은 전부 달라 "문구 다양성 100%" 로 잡혔지만 틀은 하나였습니다.

### 가설

| | 가설 | 근거 |
| --- | --- | --- |
| H1 | 문장을 **다음 행동으로 끝내면** `goal` 이 오른다 | 프롬프트에 "무엇을 말할지" 만 있고 "어떻게 끝낼지" 가 없음 |
| H2 | **상투적 도입 금지** + 재료의 구체적 성질로 열면 `differentiation` 이 오른다 | 21/25 가 같은 틀 |

부족 재료를 나열하게 하는 규칙은 **뺐습니다.** 부족분은 추천 순위가 이미 반영하므로
문구까지 재고 보고서가 될 필요가 없습니다. 다만 하나일 때는 그것을 담게 하는 것이 가장
강한 행동 유도라 이름을 적게 했습니다. 과장은 규칙이 아니라 `compliance` 항목이 거릅니다.

### 결과 (`v5`): 평균 8.24, 통과율 84%

| 항목 | v4 | v5 | 변화 |
| --- | --- | --- | --- |
| `goal` 목적성 | 4.64 | 7.64 | **+3.00** |
| `differentiation` 차별성 | 4.96 | 7.00 | **+2.04** |
| `relevance` 공감성 | 6.16 | 7.96 | +1.80 |
| `attractiveness` 주목도 | 5.52 | 7.24 | +1.72 |
| `compliance` 적절성 | 7.32 | 8.88 | +1.56 |
| `clarity` / `brevity` | 8.36 / 9.64 | 9.20 / 9.56 | +0.84 / -0.08 |

```
v4  신선한 소고기와 미나리, 연근으로 건강한 차돌박이구이를 즐겨보세요.          [7.1]
v5  고소한 차돌박이와 아삭한 미나리, 연근이 어울려 오렌지만 더하면 완성됩니다.   [8.6]
```
**H1·H2 모두 지지됩니다.** 자동 검사는 100%, 프롬프트 인젝션도 전 라운드에서 막혔습니다.

## 4. 판정자 교차 검증 — 이 보고서에서 가장 중요한 부분

`v5` 의 **같은 문구 25건**을 판정자만 바꿔 다시 채점했습니다(`--rescore`, 생성 호출 없음).
| 판정자 | 평균 | 통과율 |
| --- | --- | --- |
| `openai/gpt-4.1` | **8.24** | **84%** |
| `google/gemini-2.5-flash` | 7.37 | 60% |
| `anthropic/claude-sonnet-4` | 7.24 | 52% |

**같은 글에 1.0점, 통과율 32%p 차이가 납니다.** 통과선 7.5 를 넘느냐가 누가 채점했느냐로
갈립니다. 그런데 **항목 순위는 일치합니다.**

| 비교 | 케이스별 점수 순위 상관 | 항목 순위 상관 |
| --- | --- | --- |
| gpt-4.1 vs claude-sonnet-4 | +0.31 | **+0.86** |
| gpt-4.1 vs gemini-2.5-flash | +0.70 | **+0.60** |
| claude-sonnet-4 vs gemini-2.5-flash | +0.28 | **+0.74** |

세 판정자 모두 `goal` · `differentiation` · `attractiveness` 를 최하위 셋에, `clarity` 를 상위에
놓았습니다. **"어느 축이 약한가" 에는 합의하고, "이 문구가 몇 점인가" 와 "어느 문구가 더
나은가" 에는 합의하지 않습니다.**

### 그래서 어떻게 쓰나

| 쓸 수 있는 것 | 쓰면 안 되는 것 |
| --- | --- |
| **항목 순위** -> 다음에 무엇을 고칠지 | 평균 점수를 절대 기준으로 |
| **같은 판정자**로 잰 실험 간 비교 | 판정자가 다른 실험 간 비교 |
| 자동 검사 6종(LLM 무관, 결정적) | 문구 다양성 100%(어미만 달라도 100%) |

통과선 7.5 를 배포 게이트로 쓰려면 **판정자를 하나로 고정**해야 합니다. 결과 JSONL 첫 줄에
판정 모델이 남는 이유가 이것입니다.

## 5. 결론과 다음

**측정이 곧 개선이었습니다.** 7건 중 4건(E1·E2·E4·E7)이 "숫자를 못 믿게 된 것" 이었고 그걸
고친 뒤에야 대상을 고칠 수 있었습니다.

| | 다음 할 일 | 왜 |
| --- | --- | --- |
| 1 | 배치 재제출에 내용 해시(E1) | 안 고치면 같은 이름 입력에서 또 납니다 |
| 2 | `differentiation` 7.0 올리기 | 세 판정자 모두 최하위권. 부족 재료가 많을 때 문장이 상투적으로 돌아감 |
| 3 | 사람 평가와의 정합성 확인 | 25건 중 5~6건을 사람이 채점해 판정자와 상관 확인(`rag 평가 지표 종류.md` 5.5) |
| 4 | 검색 사용/미사용 비교 | 추천 문구에 벡터 검색이 필요한지 아직 미측정 |
| 5 | `serving` 연결 | 3차 문서(추론 API + BE/FE 인터페이스)의 전제 |

**3번을 하기 전까지는 어떤 판정자도 정답이 아닙니다.** 지금 셋의 불일치가 보여 주는 것은
"판정자가 틀렸다" 가 아니라 "기준점이 없다" 입니다.
