## 1. 영역 1 — 데이터 적재

### 1-1. 파이프라인 3단계

출처가 제각각인 raw(공공 JSON, 크롤 parquet, CSV)를 타깃 스키마로 옮깁니다.
**판단이 필요한 곳에만 LLM 을 씁니다**(OpenAI Batch API, 50% 할인).

```
raw ─▶ profile ─▶ extract ─▶ resolve ─▶ staging ─▶ 타깃 테이블
       (컬럼 의미) (행 파싱)   (재료 매칭)  (UNLOGGED)  (멱등 upsert)
```

```bash
uv run data-pipeline profile|extract|resolve --job <name>   # 배치 제출
uv run data-pipeline collect --stage resolve --job <name>   # 결과 수거
uv run data-pipeline load-catalog --apply                   # category / product
uv run data-pipeline load                                   # 레시피 / 보관기준
uv run data-pipeline load-recipes --apply                   # COOKRCP01 (LLM 없이 파싱)
uv run data-pipeline embed --target all --apply             # 임베딩
uv run data-pipeline seed-demo --users 20 --apply           # 데모 사용자/냉장고/재고
```

### 1-3. 설계 판단 셋

**열거값을 한국어로 저장합니다.** `storage_type`·`cooking_method` 등은 화면에 그대로
나갑니다. 영어로 두면 서빙에서 한 번, 프런트에서 한 번 되돌려야 하고 그 대응표가 두 벌이
되면 갈라집니다. 적재 시점에 한 벌로 모읍니다(alembic `0007`).

**모르는 값은 지어내지 않습니다.** CHECK 가 걸린 컬럼은 비우고(`storage_type` 1,551행),
아닌 곳은 원문을 남깁니다. 버린 값은 적재 리포트에 남습니다.
유일한 예외가 `stock_quantity` 로, 참값이 존재하지 않는 값이라 `seed-demo` 가 만듭니다.

**적재는 멱등입니다.** 자연키(`source_type` + `source_*_id`) 기준 `NOT EXISTS` / `ON CONFLICT`
라 몇 번을 돌려도 늘지 않고, Neon 브랜치를 갈아도 `data/artifacts/` 로 복원됩니다.
다만 **`data/` 는 gitignore 대상**이라 `ingredient_matches.json` 이 없으면 매칭률이
79.2% 가 아니라 62.8% 가 나옵니다(그 파일 하나가 16.4%p). 팀 공유가 필요하면 따로 백업하세요.

## 2. 영역 2 — 추천 SQL 카탈로그 (`recsys_sql`)

### 2-1. 무엇인가

**서빙의 repository layer 입니다.** `.sql` 파일을 서빙이 복사하지 않고 import 합니다.
복사본은 반드시 갈라지기 때문입니다.

```python
from recsys_sql.repository import prepare

sql, args = prepare("my_recipe_candidates", {"user_id": 9200000006, "min_match_rate": 0.3, "max_results": 10})
rows = await conn.fetch(sql, *args)  # :name -> $1 변환은 prepare 가
```

카탈로그는 패키지 **안**(`src/recsys_sql/queries/<github_id>/`)에 둡니다. 밖에 두면 휠에
안 담겨 이미지 첫 요청에서 죽습니다. 개발 중에는 editable 설치라 안 드러납니다.

### 2-2. 쿼리 13종 (api_spec 읽기 엔드포인트 대응 완료)

| 화면 | 쿼리 |
| --- | --- |
| 홈 버블 | `bubble_candidate_counts` · `bubble_recipe_candidates` · `bubble_products` |
| 마이냉장고 | `my_fridge_items` · `my_recipe_candidates` · `recipe_missing_ingredients` |
| 상품 | `product_detail` · `product_recipes` · `product_storage_guideline` |
| 레시피 | `recipe_detail` |
| 템플릿 | `fridge_recipe_match` · `missing_ingredient_products` · `reorder_candidates` |

`uv run recsys-sql list` 로 파라미터까지 봅니다. 파라미터 타입은 `catalog.py` 가 검증합니다.

### 2-3. 성능 체크포인트

홈 화면 첫 쿼리가 `EXPLAIN (ANALYZE, BUFFERS)` 기준 **232,931 블록 / 335ms** 였습니다.
집계가 (버블 x 레시피) 쌍마다 돌아 5,430번 반복되고 있었습니다. 레시피당 한 번만
집계하도록 뷰를 다시 짜서(alembic `0010`) 아래가 됐습니다.

```
bubble_candidate_counts    232,931 블록 335ms  ->    416 블록  30ms
bubble_recipe_candidates    46,698 블록  63ms  ->    415 블록  15ms
bubble_products             49,645 블록  73ms  ->  5,375 블록  27ms
```

결과 집합은 동일하고 `test_bubble_queries.py` / `test_query_grain.py` 가 고정합니다.
**버퍼는 EXPLAIN 루트 노드 기준**입니다 - 상위 노드에 하위 값이 누적 보고되므로
재귀로 더하면 중복으로 셉니다.

## 3. 영역 2 — 추천 문구 생성 (`rag_lab`)

### 3-1. 용도를 좁혔습니다

`rag_lab` 은 **추천 문구 생성 전용**입니다. 열린 질문 챗봇이 아닙니다. 보관법은 RAG 가
아니라 API 클릭 시 DB 조회로 갑니다(그래서 `storage_guideline` 에 embedding 이 없습니다).

```python
from rag_lab import recommendation_reason, RecommendationCase

reason = await recommendation_reason(case, chat=chat)
# "고소한 차돌박이와 아삭한 미나리, 연근이 어울려 오렌지만 더하면 완성됩니다."
```

**이 경로는 검색을 쓰지 않습니다.** 입력이 `my_recipe_candidates` 가 준 구조화된 값이라
벡터 검색을 한 번 더 도는 것은 지연과 비용만 늘립니다. 그래서 DB 도 열지 않습니다.

### 3-2. 공급자 교체가 `.env` 한 줄

```bash
LLM_PROVIDER=openrouter        # openai | openrouter | anthropic | custom
LLM_MODEL=openai/gpt-4.1-mini
JUDGE_MODEL=openai/gpt-4.1     # 평가용. 생성 모델과 같으면 실행 거부
```

채팅·임베딩·판정이 각자 공급자를 해석합니다. **공급자나 주소를 따로 지정하면 키도 따로
받습니다** - 채팅 키를 물려주면 그 키가 다른 회사 엔드포인트로 그대로 나갑니다.

### 3-3. 품질 검증 2단 (판단은 LLM 이, 불변식은 코드가)

| 층 | 무엇 | LLM |
| --- | --- | --- |
| 자동 검사 6종 | 환각 재료 · 보유 뒤집힘 · 상비재료 구매유도 · 조리시간 지어냄 · 길이 · 빈 문구 | **안 씀** |
| 루브릭 8항목 | `rag 평가 지표 종류.md` 7절. 0~10점, 평균 7.5 통과 | 씀 |

```bash
JUDGE_MODEL=openai/gpt-4.1 uv run rag-lab recommend --name v5 --judge \
  --cases rag_lab/experiments/openLeeWorld/cases.jsonl
```

현재 상황 25건에서 **자동 검사 100% / 루브릭 평균 8.24 / 통과율 84%** 입니다.
숫자의 해석과 한계는 2차 실험 보고서를 보세요.
