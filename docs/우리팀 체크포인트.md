# 검색 레시피 추천

## 버블 (홈 화면)

- [x] 버블 키워드는 코드가 아니라 데이터(`bubble_keyword`)다. 라벨과 규칙을 배포 없이 바꾼다.
- [x] 후보가 `min_candidates`에 못 미치는 버블은 화면에 내지 않는다.
- [x] 버블 규칙의 해석은 한 곳(`bubble_recipe_candidate` 뷰)에만 있다. 레시피 목록과 상품 목록이 같은 규칙을 본다.
- [x] `재료 적게 드는 요리`는 재료 수 임계값을 지킨다.
- [x] `15분 안에 끝나는 요리`는 조리시간 조건을 지킨다.
- [x] `고기 든든하게`는 달걀만 든 후식을 고기 요리로 치지 않는다.
- [x] 버블 목록은 라벨과 설명을 함께 낸다.

## 버블로 여는 상품

- [x] 버블을 눌러 나오는 상품은 그 버블의 레시피가 실제로 쓰는 재료의 상품이다.
- [x] 상비 재료 상품이 버블 상품 목록을 채우지 않는다.
- [x] 상품 목록은 페이지를 넘겨도 같은 상품이 두 번 나오지 않는다.
- [x] 상품 목록은 다음 페이지가 있는지를 응답으로 알려 준다.

## 상품 / 레시피 상세

- [x] 상품 상세는 구성 재료를 한 번의 조회로 함께 낸다.
- [x] 구성 재료가 하나도 없는 상품도 상세는 나온다.
- [x] 상품으로 만들 수 있는 레시피는 재료를 경유해 찾는다.
- [x] 선택 재료로만 걸치는 레시피는 그 상품의 레시피 후보가 아니다.
- [x] 레시피 상세는 재료줄과 조리 단계를 함께 내고, 조리 단계는 순서대로다.
- [x] 상품 하나의 보관법은 대표 재료가 정확히 하나일 때만 알려 준다.
- [x] 같은 재료에 보관 기간이 여럿이면 가장 짧은 것을 쓴다.

## 검색 기반

- [x] 임베딩을 만든 텍스트는 검색 결과 본문에 그대로 보인다. (검색은 됐는데 근거가 비는 상태를 막는다)
- [x] 열거값은 한국어로 저장한다(보관 유형·위치·상황, 기간 단위, 조리법).

# my 냉장고 & my 레시피

## 보유 판정

- [x] 냉장고는 재료가 아니라 상품을 담는다. 재료는 `product_ingredient(role='PRIMARY')`로 푼다.
- [x] PRIMARY가 아닌 구성 재료는 보유로 치지 않는다.
- [x] 유통기한이 지난 냉장고 상품의 재료는 보유로 치지 않는다.
- [x] 상비 재료는 냉장고에 없어도 보유한 것으로 친다.
- [x] 냉장고 목록은 유통기한이 지난 항목을 숨기지 않고 표시만 달리한다.
- [x] 냉장고 목록은 한 칸이 한 행이다.

## 레시피 추천

- [x] 마이 레시피 후보는 필수 재료 커버리지 순으로 정렬한다.
- [x] 커버리지가 같으면 조리시간이 짧은 쪽이 먼저다.
- [x] `min_match_rate` 미만인 레시피는 후보에서 뺀다.
- [x] 냉장고 재료를 하나도 쓰지 않는 레시피는 후보가 아니다.
- [x] 선택 재료는 커버리지 계산에 넣지 않는다.

## 부족 재료

- [x] 부족 재료 목록과 부족 개수는 서로 어긋나지 않는다.
- [x] 부족 재료는 어디서 충족됐는지로 나뉜다(`BASE` / `IN_FRIDGE` / `PANTRY` / `MISSING`).
- [x] 상비 재료는 부족 재료로 보고하지 않는다.
- [x] 로그인하지 않은 사용자도 레시피의 재료 목록은 받는다.
- [x] 부족 재료를 채울 상품은 레시피 지정 상품 > 인기도 > 낮은 가격 순이다.
- [x] 품절이거나 비활성인 상품은 추천하지 않는다.
- [x] 한 레시피에 지정 상품이 여러 칸 있어도 레시피가 중복으로 나오지 않는다.

## 재구매

- [x] 재구매 후보는 마지막 구매 후 일정 기간이 지난 상품만이다.
- [x] 냉장고에 아직 유효하게 남아 있는 상품은 재구매 후보에서 뺀다.
- [x] 냉장고에 있어도 유통기한이 지났으면 재구매 후보다.
- [x] 품절 상품은 재구매 후보가 아니다.

## 추천 문구 (LLM)

- [x] 추천 문구는 냉장고 상황을 입력으로 받고, 벡터 검색도 DB 조회도 하지 않는다.
- [x] 추천 문구는 상황에 없는 재료를 지어내지 않는다.
- [x] 추천 문구는 보유 재료를 "있다", 부족 재료를 "없다"로만 말한다.
- [x] 추천 문구는 상비 재료를 사라고 하지 않는다.
- [x] 추천 문구는 조리시간이 주어지지 않으면 시간을 언급하지 않는다.
- [x] 추천 문구는 60자를 넘지 않고, 빈 문구는 실패로 잡는다.
- [x] 문구 품질은 8항목 루브릭으로 0~10점을 매기고 평균 7.5 이상이면 통과다.
- [x] 채점 모델은 생성 모델과 달라야 한다. 같으면 조립 시점에 거부한다.
- [x] 실험 결과에는 실제로 돈 모델 이름이 기록된다.
- [x] 옛 결과를 재채점할 때 상황이 바뀌었으면 거부한다. 확인 못 한 결과에 지문을 찍지 않는다.

# api 서빙 서버

## 응답 계약

- [x] 모든 응답은 `{status, message, data, error, timestamp}` 다섯 필드를 항상 담는다. (백엔드 Spring `ApiResponse`와 같은 계약)
- [x] `data`가 없어도 `null`로 자리를 지킨다. FE 파서가 하나면 된다.
- [x] `timestamp`는 UTC 초 단위 고정 포맷이다.
- [x] 실패 응답의 `error`는 에러 코드 이름이고, 코드마다 HTTP 상태가 정해져 있다.
- [x] 검증 실패와 없는 경로도 같은 envelope으로 답한다.

## 경로와 가용성

- [x] 추천 엔드포인트는 `/api/v1` 아래에만 있다. 접두사 없는 옛 경로는 없다.
- [x] 헬스체크는 envelope을 쓰지 않고 liveness와 readiness로 나뉜다.
- [x] liveness는 DB를 건드리지 않는다. DB가 흔들려도 컨테이너가 재시작되지 않는다.
- [x] DB가 없어도 앱은 뜬다. DB가 필요한 엔드포인트만 503으로 답한다.
- [x] 입력 범위 검증은 DB에 가기 전에 422로 끝난다.

## SQL 단일 출처

- [x] 서빙은 자기 `.sql` 파일을 갖지 않는다. 생기면 테스트가 실패한다.
- [x] 노출하는 쿼리는 화이트리스트에 적힌 것뿐이고, 그 이름은 전부 카탈로그에 실재한다.
- [x] 카탈로그 쿼리는 전부 파라미터 계약을 선언하고, 빠지거나 타입이 틀리면 DB에 가기 전에 걸린다.
- [x] 카탈로그에 쓰기 문장은 들어올 수 없다.
- [x] 쿼리마다 한 행의 단위를 선언하고, 실제 결과가 그 단위로 유일하다.
- [x] repository 계층은 SQLAlchemy를 끌어오지 않는다.

## 보안 / 성능

- [x] 로그와 헬스 응답에 DSN·호스트·자격증명이 남지 않는다.
- [x] `ENVIRONMENT`가 `local`이 아니면 `/docs`와 `/openapi.json`을 닫는다.
- [x] 커넥션 풀은 앱 기동에 한 번 만든다. 요청마다 새로 붙지 않는다.
- [x] pooler 주소면 statement 캐시를 끈다.
- [x] 추천 쿼리는 금지된 테이블에 순차 스캔을 걸지 않는다.
- [x] 버블 쿼리는 정해진 버퍼 예산 안에서 끝난다.
