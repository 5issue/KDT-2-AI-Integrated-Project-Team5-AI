# PostgreSQL & Neon 환경 EXPLAIN 핵심 성능 체크리스트

PostgreSQL 옵티마이저의 비용 기반 판단(CBO) 원리와 시간 복잡도, 그리고 서버리스 환경인 **Neon(Serverless Postgres)**의 특성을 반영한 실행 계획 분석 가이드입니다.

---

## 1. EXPLAIN 필수 명령어 및 Neon 팁
실행 계획을 확인할 때는 단순히 `EXPLAIN`만 쓰지 말고, 반드시 아래 옵션을 조합하여 실행하세요.

```sql
EXPLAIN (ANALYZE, BUFFERS, TIMING)
SELECT ... ;
```
* **ANALYZE**: 쿼리를 실제 실행하여 실측 데이터를 수집합니다. (DML 쿼리에 사용할 경우 트랜잭션 롤백 주의)
* **BUFFERS**: ⭐️ **Neon 환경 핵심** ⭐️ 데이터가 메모리(Shared Buffers)에서 읽혔는지, 디스크(로컬 캐시 또는 Neon Storage)에서 읽혔는지 보여줍니다.

## 2. 5대 핵심 성능 체크리스트

### ① 스캔 방식 확인 (Scan Type)
구조적 결함이나 인덱스 누락 여부를 시간 복잡도 기준으로 판단합니다.

* **Index Scan / Index Only Scan ($O(\log N)$)**: **[최상]** 필요한 데이터만 인덱스 트리를 통해 정확히 짚어냅니다. 특히 `Index Only Scan`은 테이블 블록을 방문하지 않고 인덱스만으로 결과를 반환하여 가장 빠릅니다.
* **Bitmap Index Scan ($O(\log N) + \alpha$)**: **[양호]** 조건을 만족하는 행들의 주소(TID)를 비트맵으로 모은 뒤, 테이블 블록을 모아서 랜덤 I/O를 최소화하며 방문합니다.
* **Sequential Scan (Seq Scan) ($O(N)$)**: **[경고]** 테이블 전체를 처음부터 끝까지 다 읽는 Full Scan입니다. 대용량 테이블에서 발생한다면 인덱스 누락 또는 컬럼 가공(예: `WHERE TO_CHAR(date, ...) = ...`)으로 인해 인덱스가 무력화되었는지 확인해야 합니다.

### ② 조인 알고리즘 확인 (Join Algorithm)
결합 방식과 메모리(work_mem) 활용도를 체크합니다.

* **Nested Loop ($O(M \cdot \log N)$)**: **[소량 데이터 최적]** 선행 테이블의 행을 하나씩 읽으며 후행 테이블의 인덱스를 탐색합니다. 안쪽 테이블에 조인 키 인덱스가 없으면 $O(M \cdot N)$으로 치솟아 시스템이 마비됩니다.
* **Hash Join ($O(M + N)$)**: **[대량 데이터 최적]** 한쪽 테이블로 메모리에 해시 테이블을 만들고, 다른 테이블을 스캔하며 매칭합니다. 대용량 조인에 유리하지만 메모리가 부족하면 디스크를 사용하여 느려집니다.
* **Merge Join ($O(M \log M + N \log N)$)**: 양쪽 테이블이 조인 키로 정렬되어 있을 때 순차적으로 병합합니다.

### ③ 비용(Cost)과 실제 실행 시간(Actual Time)의 괴리
옵티마이저의 예측치(`rows=...`)와 실제 수행 결과(`rows=... loops=...`)를 비교합니다.

* **괴리가 큰 이유**: DB 통계 정보가 최신화되지 않았기 때문입니다. 옵티마이저가 10건이 나올 줄 알고 `Nested Loop`를 선택했는데 실제 1,000만 건이 터지면 장애로 이어집니다.
* **체크 포인트**: 두 수치의 차이가 10배 이상 난다면 통계 정보 갱신이 필요합니다.

### ④ 디스크 I/O 및 필터 효율성 (Filter vs Index Cond)
* **`Index Cond`**: 인덱스 단계에서 불필요한 행을 원천 차단한 최적의 상태입니다.
* **`Filter` / `Rows Removed by Filter`**: 데이터를 메모리로 읽어온 후 CPU 연산으로 지운 행의 개수입니다. 이 수치가 수만~수백만 건에 달한다면 인덱스 구성 순서를 바꾸거나 복합 인덱스를 고려해야 합니다.

### ⑤ 정렬 및 그룹화 영역 (Sort / Aggregate)
* **`Sort Method: quicksort Memory: ...`**: 정렬 작업이 메모리 내에서 안전하게 종료되었습니다.
* **`Sort Method: external merge Disk: ...`**: **[위험]** 정렬 데이터가 `work_mem` 설정을 초과하여 **디스크(임시 파일)를 사용**했다는 뜻입니다. 성능이 급격히 저하되므로 인덱스를 통해 정렬을 생략하거나 `work_mem`을 확장해야 합니다.

## 3. Neon(네온) 환경 특화 체크 팁 💡

Neon은 가상화된 계산 노드(Compute Node)와 분산 저장소(Pageserver/Safekeeper)가 분리된 **서버리스 아키텍처**입니다. 따라서 일반적인 로컬 DB와 다른 관점의 튜닝이 필요합니다.

### ① `BUFFERS` 지표 해석법 (Cold Read와 Storage Latency)
`EXPLAIN (ANALYZE, BUFFERS)` 실행 시 출력되는 Buffer 항목을 다음과 같이 해석합니다.
* **`shared hit`**: 계산 노드의 로컬 메모리(RAM) 캐시에서 즉시 읽음 **(가장 빠름)**
* **`shared read`**: 로컬 메모리에 없어 Neon 스토리지(Pageserver)에 요청하여 읽음 **(네트워크 레이턴시 발생)**
* 만약 특정 쿼리에서 `shared read` 비중이 계속 높다면, 서버리스 노드가 잠들었다가 깨어난 **Cold Start 상태**이거나, 인덱스가 비효율적이어서 스토리지로부터 너무 많은 페이지를 실시간으로 받아오고 있다는 방증입니다. 인덱스 최적화를 통해 `shared read` 패킷 수 자체를 줄여야 합니다.

### ② 오토스케일링(Autoscaling)과 `work_mem`의 한계
* Neon은 트래픽에 따라 CPU/RAM이 자동으로 늘어나지만(Autoscaling), 개별 쿼리가 쓸 수 있는 **`work_mem` 단위 설정은 보수적으로 잡혀있는 경우가 많습니다.**
* 이로 인해 대량의 `Sort`나 `Hash Join` 발생 시 앞서 말한 `external merge Disk` 현상이 일반 DB보다 더 자주 발생할 수 있습니다. 쿼리 실행 전에 `SET work_mem = '64MB';`와 같이 세션 단위로 메모리를 명시적으로 늘려주고 수행하는 팁이 유용합니다.

### ③ 실시간 통계 오차 대응
* Neon은 분산 스토리지 구조 특성상 대량의 쓰기(Write) 작업 직후 통계 정보 반영에 미세한 지연이 있을 수 있습니다.
* 배치 작업이나 대규모 이관 직후 `EXPLAIN` 예측이 크게 틀어진다면, 쿼리 수행 전 명시적으로 **`ANALYZE 테이블명;`**을 실행하여 통계 정보를 강제 동기화하세요.
